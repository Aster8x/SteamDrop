# Decisions

Why things are the way they are. Newest decisions go at the bottom of each section.

## Project and code

- **Coding approach:** the smallest change that fully works, no speculative options, standard library first, and a small test for every non-trivial piece of logic.
- **Commit identity:** commits use the repository owner's GitHub identity (the same one as the initial commit).
- **Stack:** Tauri 2 with a Rust backend and a plain HTML/CSS/JS front end loaded straight from `ui/` (`withGlobalTauri`, no bundler, no framework). Dev tooling is only `@tauri-apps/cli`.
- **Dependencies kept minimal:** `notify` (folder events), `reqwest` (HTTP, the same version the updater already pulls in), `ab_glyph` + `png` (title cards), `crc32fast` (shortcut ids), `winreg` (Steam path, run on startup), plus Tauri's dialog, notification, single-instance and updater plugins. `png` and `reqwest` match the versions Tauri already uses, so nothing gets compiled twice.
- **TLS uses Windows' own stack** (`native-tls` / Schannel) instead of rustls. That means no C code to compile (`ring`) and a smaller binary.
- **The binary is named `SteamDrop.exe`** (`mainBinaryName`), so Task Manager and the uninstaller show a recognizable name.
- **Strict CSP and minimal permissions:** the window only has `core:default`. Folder and file pickers, opening links and folders all go through SteamDrop's own commands, which check their input (`open` accepts only `https://` links or existing folders).

## Steam

- **Own binary VDF reader/writer** (`vdf.rs`, ~100 lines) instead of a crate. It keeps every entry and field in order, including ones it doesn't know, so other tools' shortcuts survive untouched. If it finds a field type it doesn't understand, it refuses to write rather than guess.
- **Shortcut id** = `crc32(quoted exe + name) | 0x80000000`, stored in the shortcut's `appid` field. The same number names the grid art files.
- **Every Steam account on the PC** gets the shortcut by default ("per Steam user"). Accounts are the numeric folders under `userdata` that have a `config` folder. "Add games to: Only these accounts" limits adding to the selected ones. They're shown by their Steam persona name from `config/loginusers.vdf`, where SteamID64 = 76561197960265728 + the folder number; a small text-VDF parser was added for that file. Removing (a game, pending removals, uninstall cleanup) always goes through **every** account, so nothing is left behind after the selection changes. SteamDrop's own shortcut follows the same selection.
- **Steam must be closed while `shortcuts.vdf` changes**, or Steam may overwrite it later. SteamDrop asks Steam to close (`steam.exe -shutdown`), waits until it has exited (checked every half second, up to a minute, and only during a restart), writes, then starts Steam again: in Big Picture (`-tenfoot`) after adding games, as before after removing them.
- **If Steam is open and the user declines a restart,** SteamDrop still writes the change and says "Restart Steam to see it". If Steam later overwrites the file, the game shows a **Not in Steam** badge with an **Add to Steam again** button. Waiting for Steam to close by itself would have needed polling.
- **Artwork is fetched before Steam closes,** so Steam is only down for the few seconds the write takes. Games found together are added with a single restart.
- **Backups:** before every write, `shortcuts.vdf` is copied to `%APPDATA%\SteamDrop\backups\<account>\shortcuts-<unix time>.vdf`. The newest 30 per account are kept. Writes go to a temporary file and are then renamed, so a crash can't leave a half-written file.
- **`LastPlayTime` is set to now** so new games appear first under Recent.
- **Re-adding a folder** under a different name or exe removes the old shortcut in the same step, so there are no duplicates.

## Watching folders

- **Event-based only:** `notify` uses Windows' `ReadDirectoryChangesW`, one recursive watch per watched folder. Timers exist only while a folder has recent changes; nothing is scanned periodically.
- **"Copying has finished"** means no change in that game folder for 12 seconds, and no recently changed file in it is still open (an exclusive open succeeds). If a file is still open, SteamDrop checks again 12 seconds later.
- **One game per direct subfolder.** A changed path maps to a game through one shared rule (`watcher::game_folder`): take the most specific watched folder that contains the path, then its first folder below. Nothing maps when that folder is itself watched (so `Games` skips `Games\Torrent`) or when the path or the game folder is inside an excluded folder. The startup scan, Scan now, Add existing games now and the "games already here" count all use the same rule (`watcher::subfolders`).
- **Exclusions** are stored as full paths (`excluded` in settings) and shown under the innermost watched folder that holds them. A new exclusion must be inside that watched folder. Changing exclusions restarts watching. Exe candidates inside an excluded folder are dropped too.
- **Moves:** Windows reports a folder moved or renamed into a watched folder as one event for its new path. Since every event kind counts, a move goes through the same quiet-period and copy checks as a copy. A test renames a folder into a watched folder and checks the event maps to it. Folders moved *out* are never removed automatically: the game shows under **Missing games** with "Find it" (choose the new folder; the same file inside it is used if it's there, otherwise the best guess) and "Remove from Steam". If a missing game's folder name turns up in a watched folder, SteamDrop treats it as that game moved and replaces its shortcut instead of adding a second one.
- **Never twice in Steam:** before adding, SteamDrop compares the game file with every shortcut's exe in every Steam account, normalized for quotes, slashes and case. A match on a shortcut that isn't one of SteamDrop's own games stops the add; watched folders skip such games silently, with a log line.
- **Starting fresh** is the default. When a watched folder already holds games, "Only new games from now on" is the focused button, and it records them as a baseline. "Add existing games now" clears that baseline for the folder's non-game subfolders and runs them through the normal pipeline.
- **Folders that appeared while SteamDrop was closed** are picked up by a one-time scan when watching starts. SteamDrop remembers the folders it has handled ("known"), so this never repeats work.
- **Adding a watched folder that already has folders in it** asks whether to add those games too or only new ones. Otherwise a big existing library would either be ignored silently or added all at once without asking.
- **Empty new folders are ignored** until files arrive (for example a "New folder" that is about to be renamed).
- **Manual mode:** the SteamDrop window opens with a "New game found" card where the user can change the name and the exe. **Not now** means "don't ask about this folder again". An "Only an installer found" card appears in the same place.

## Picking the exe

- **Score** = name similarity to the cleaned folder name (0 to 50 points: exact match, initials like `GTA5` for "Grand Theft Auto V", containment, then bigram overlap), plus file size (log scale, -10 to +16), minus 12 points per folder level, minus 6 for "launcher"/"config". Deeper and tinier files lose. For Unreal games this picks the small top-level starter exe, which is what Steam does too.
- **Excluded by name:** uninstallers, setup/installers, crash handlers and reporters, redistributables (VC++, DirectX, .NET, PhysX, OpenAL), anti-cheat installers, updaters, web helpers, and similar. **Excluded folders:** `_CommonRedist`, `redist`, `__Installer`, `DirectX`, `Support`, `tools` and similar. The scan goes 4 levels deep and stops after 20,000 entries.
- Plain words like "crash" are not excluded on their own, so a game named "Crash ..." isn't skipped.
- **Folder name cleaning** drops `[tags]`, `(tags)`, version numbers (`v1.2.3`, `build 1234`) and underscores. Dots are kept unless a number follows, so "S.T.A.L.K.E.R." survives.
- **Installer only:** a `setup*.exe`, `*install*.exe` or `.msi` near the top of the folder, and no game exe candidates at all.

## Artwork

- **Order per slot:** SteamDrop's cache → the game folder's `SteamDrop art` folder (if present) → official Steam art → SteamGridDB → title card. Each slot falls back on its own, so one missing official image doesn't throw away the others.
- **Finding the Steam App ID:** `steam_appid.txt` anywhere in the top 3 levels of the folder (emulators often keep it in `steam_settings`). **Added:** if there is none, an *exact* title match in Steam's public store search. Many DRM-free games have a Steam page but no `steam_appid.txt`, and official art is the cleanest. Only exact matches count, to avoid wrong art. The user can enter or correct the App ID in the details window, which re-fetches the art.
- **Steam CDN files:** `library_600x900_2x.jpg` (falling back to `library_600x900.jpg`), `header.jpg` for the wide slot (the same shape as 920×430), `library_hero.jpg`, `logo.png`. Both `shared.steamstatic.com/store_item_assets` and `cdn.cloudflare.steamstatic.com` are tried. Files under 1 KB or that aren't PNG/JPEG are rejected (placeholders).
- **SteamGridDB:** static images only, with NSFW, humor and epilepsy-warning images filtered out. Searching by title only counts when the best match's name is close (similarity ≥ 0.6). With a Steam App ID, SteamDrop asks for that game directly.
- **Icon fallback:** when no real icon is found, the shortcut's icon points at the game's exe, so Steam shows the game's own icon. That looks better than a text square.
- **Title cards** are drawn in Rust with the bundled Pixelify Sans font in Night Grove's colors: a dark gradient and a thin accent stripe, with the title word-wrapped at the largest size that fits. The hero gets no text (Steam lays the logo over it), and the logo is text on a transparent background with a soft shadow, so it reads well over any background.
- **Grid files** are `<id>p`, `<id>`, `<id>_hero`, `<id>_logo` and `<id>_icon`, with the image's real extension. Old files with other extensions are removed first.
- **No game artwork is in the repository.** The app icon is an original drop-and-arrow design made for SteamDrop, with no Steam logo.

## App behavior

- **Data lives in `%APPDATA%\SteamDrop`** (`data.json`, `art`, `info`, `backups`), as specified, rather than Tauri's per-identifier folder. Only the WebView's own cache uses the identifier folder.
- **Automatic mode** isn't stored. It's derived from its three sub-settings: all on shows On, all off shows Off, a mix shows Custom. Pressing it while it shows Custom turns everything on. "Show notifications" is part of it, so it is off by default too. In manual mode the window opens itself instead.
- **Tray:** closing the window destroys it, freeing the WebView's memory, and the app keeps running. It's recreated from the tray or when a new game needs confirming. With "Keep running in the tray" off, closing quits.
- **Run on startup** writes `HKCU\...\Run\SteamDrop = "SteamDrop.exe" --tray`. That is the value Tauri's uninstaller already removes, so no autostart plugin is needed.
- **"Open Steam in Big Picture when Windows starts"** is its own entry in Windows' startup list (`SteamDrop Big Picture` = `SteamDrop.exe --start-big-picture`), separate from "Run when Windows starts", so it works even when SteamDrop doesn't stay running. That short-lived process waits 8 seconds (sign-in, and Steam's own autostart if it has one), checks whether the "Steam Big Picture Mode" window already exists, and otherwise opens `steam://open/bigpicture`. That starts Steam if needed or switches a running Steam to Big Picture. The uninstaller removes the entry.
- **Single instance:** starting SteamDrop again just shows the existing window.
- **Store details** (description, developer, publisher, genres, release date) come from `store.steampowered.com/api/appdetails`, fetched on first open and cached in `info/<appid>.json`.
- **Wording** is aimed at non-technical users: "Game file" instead of "executable", "Not now" instead of "Ignore", and every Steam restart is explained before it happens.
- **Look:** Night Grove (dark) by default, with Day Grove and other themes in Settings and a sun/moon button in the sidebar; see "Night Grove" below. Base text is 18 px and buttons are at least 44 to 52 px tall.

## Installer, uninstaller, releases

- **Custom NSIS template** (`src-tauri/windows/installer.nsi`, copied from tauri-bundler 2.10.4). Tauri's hooks can't add uninstaller checkboxes, so the confirm page was changed to show two, both unchecked:
  1. "Remove SteamDrop's games from Steam (and their art)", with the note that Steam then hides their playtime. This runs `SteamDrop.exe --uninstall-cleanup` *before* the program files are deleted, since SteamDrop is what knows which shortcuts it added. The cleanup closes and restarts Steam if it's running, and backs up `shortcuts.vdf` first, like every change.
  2. "Delete SteamDrop settings and cache" deletes `%APPDATA%\SteamDrop` plus Tauri's own data folders.
- **Per-user install** (no admin prompt), English only, WebView2 bootstrapper downloaded if missing.
- **Release asset is renamed to `SteamDrop-Setup.exe`** and `latest.json` is written by the workflow, so the README's download button can point at the fixed URL `releases/latest/download/SteamDrop-Setup.exe`. The updater installs in passive mode (a progress bar, no questions).
- **The updater public key is a placeholder** until the owner makes a key (see `docs/RELEASING.md`). The release workflow refuses to run with the placeholder, without the secret, or when the tag doesn't match the version.
- **Recycle Bin tests are strict on Windows:** on a fixed drive the folder must be gone, and the Recycle Bin must hold one more item with at least the folder's data. The test prints the before and after numbers into the CI log. A second test sends the same folder through `\\localhost\C$` (a network path) and must be refused untouched. The strict test is skipped only under Wine outside CI, because Wine moves folders to its trash but doesn't report Recycle Bin contents.
- **CI actions** are on versions that run on Node 24 (`actions/cache@v5`, `actions/upload-artifact@v6`), so there are no deprecation warnings.
- **A build check runs on every push**, producing an unsigned installer as a workflow artifact for testing. Builds without the signing key use `src-tauri/tauri.no-updater.conf.json`, which turns off the updater files. It's a file rather than inline JSON on the command line because PowerShell mangles the quotes (that broke the first CI build).
- **Semantic Versioning, starting at 0.1.0.** The version is written in `package.json`, `tauri.conf.json` and `Cargo.toml` (the user asked for all three), and `scripts/version.mjs` keeps them and both lock files in sync. A small Node script with no dependencies is less error-prone than editing five files by hand. Every build checks that they agree.
- **Release notes come from `CHANGELOG.md`** (Keep a Changelog format). The release workflow refuses a tag whose version has no changelog section, and uses that section both on the GitHub release page and in `latest.json`. `bump` turns "Unreleased" into the new version's section and updates the compare links at the bottom.
- **The app reads its version from Tauri's package info**, which comes from `tauri.conf.json`. It's shown in About and in the tray tooltip ("SteamDrop 0.1.0").

## Sound

- **The sounds are synthesized in code** (`chime.rs`), 16-bit mono WAV in memory, 1 to 1.4 seconds: "Soft chime" (A5 then E6, pure tones with a slightly detuned copy, soft attack and fade), "Retro coin" (square-wave B5 then E6) and "Pop" (a sine dropping from 1100 to 330 Hz with a quick fade). No audio file from anyone else is involved.
- **Played by the tray app with Windows' `PlaySound`** (asynchronously, from memory), so it works with no window open and is mixed with whatever else is playing, Big Picture included. Volume is applied when the sound is made, so it doesn't change the system volume. A new chime stops the previous one before its memory is replaced.

## Secrets, logs and bug reports

- **SteamGridDB key in Windows Credential Manager** via the `keyring` crate (Windows backend only, with no extra C code). Using a well-tested crate is safer than hand-written Credential Manager calls. The key never goes into `data.json`, the logs or bug reports. The bug report also scrubs the key's text, in case it ever ended up in a log line. No migration from the settings file was written, because no released version ever stored the key there.
- **The key box loads the saved key** so it can show dots and reveal it while the eye is held. Reveal works only while held: pointer capture keeps it shown while the mouse or finger moves off the button, and Space/Enter key-down shows it until key-up. Losing focus always hides it.
- **The uninstaller's "Delete SteamDrop settings and cache" also forgets the key** (`SteamDrop.exe --forget-secrets`), since Credential Manager isn't a folder it can delete.
- **Own small logger** (`log.rs`) instead of a logging framework. It writes one plain-language line per event with a local timestamp (the `time` crate is already used by Tauri), writes one file per day and keeps 14 days, at most 20 MB in all. Today's file stays open, so logging a line is one append; the clean-up runs only when the day changes or SteamDrop starts. The log records what users and helpers care about: folders found or skipped and why, the exe and App ID chosen, where each picture came from, Steam restarts, settings changes, and problems marked "Problem:".
- **Bug report** is Markdown so it renders nicely in a GitHub issue. Every `\Users\<name>` (any drive, either slash) becomes `\Users\<user>`. Settings are listed with any key, token or password fields dropped. It's copied with the browser clipboard; if that's blocked, the report is shown in a box to copy by hand.

## Updates

- **Built on Tauri's updater** and the release's `latest.json`. The update window shows every changelog section between the installed and the new version. They come from `CHANGELOG.md` at the new version's tag on GitHub, falling back to the release notes if that can't be fetched. "What's new" uses the changelog built into the app, so it works offline.
- **Checks:** 20 seconds after startup (so startup stays quick) and every 24 hours while running, each only if its setting is on. A failed check is logged in plain words and otherwise silent. Only "Check now" shows a message.
- **"Skip this version"** is remembered in settings and only affects automatic checks; "Check now" always shows what's available. **"Remind me later"** just closes the window until the next check.
- **Automatic installs** download right away, but install only when no game started from Steam is running. That means Steam's `RunningAppID` is 0 and none of SteamDrop's games' .exe files are running, checked every 5 minutes while an update waits. Installing restarts SteamDrop (the installer reopens it with the same arguments), and the startup after an update shows a notification and the one-time "What's new" screen.
- **Update notifications always show,** even with "Show notifications" (part of Automatic mode) off, because they were asked for separately.
- **Dialogs focus their main button,** so pressing Enter never picks "Skip" or "Cancel" by accident.

## Fixes from the first laptop test

- **Settings lost after a restart (root cause):** any failed read or parse of `data.json` made SteamDrop start from defaults, and startup saves right away, so the defaults replaced the real file. Two ways a read could fail on Windows: another SteamDrop process (the tray app and the one Steam starts, around a view switch or Steam restart) replacing the file at that instant, or a broken file left by two processes writing the same `data.json.tmp` at once. A test showed that collision fails on Windows with "File not found". The data folder also came from the `APPDATA` variable, silently falling back to the Temp folder if it was missing, and windows sent all settings on every change, so a window with an old copy could put old values back. Now:
  - the folder comes from Windows' Roaming AppData location;
  - reads retry for up to a second;
  - every save goes to the process's own temporary file and is renamed into place, after the previous good file is copied to `data.json.bak`;
  - an unreadable `data.json` is kept as `data.json.broken-<time>`, logged in plain words, and recovered from `data.json.bak`;
  - settings changes are sent as the changed fields only and merged in the backend (bad values are refused).
  
  A test saves a full setup and checks that every restart path keeps it.

- **Art protocol instead of Tauri's asset protocol:** both windows load game art from `art://<game id>/<slot>` (on Windows `http://art.localhost/...`), served by SteamDrop from its art cache. Only a number and a known slot name are accepted, so nothing else on disk can be reached. The asset protocol needed the file path to match an allowed scope, which breaks when AppData is behind a link or redirected folder. Its scope and the `protocol-asset` feature are gone. If an image still fails, the page swaps it for a title card. The Couch detail view used to build `<img src="">` for games without a cover, which always shows a broken icon.
- **Blank "Window view":** Tauri runs synchronous commands on the main thread, and `run_on_main_thread` then runs immediately. So the new window's WebView2 was created inside the old window's own command callback, a known Windows deadlock: blank window, and the old view never closed. All window commands (open, switch, hide, close) are async now, so the work is queued on the event loop. Windows have a dark background colour so they never flash white.
- **One source of truth for the game list:** the app re-reads `data.json` whenever its timestamp changes (another SteamDrop process, or anything else, wrote it). It does this before showing state and before every save, so a stale copy can't overwrite newer data. A `data.json` that fails to parse is kept as `data.json.broken` instead of being replaced by an empty list. Both views also refresh when they're shown or focused.
- **Steam restart mode** is decided in one place (`steam::reopen_in_big_picture`) right before Steam is closed. It's used for adding, removing, Couch mode's restart, pending changes and the uninstaller. "Keep current mode" reopens Big Picture only if the "Steam Big Picture Mode" window exists at that moment. The launch flag that used to decide this for Couch mode was removed.
- **"Show SteamDrop in my Steam library"** is written right away only while Steam is closed. Otherwise it's a pending change (`pending_self`) applied with the other pending changes. Turning it off removes only SteamDrop's own shortcut and its grid art, from every account; a test checks that a game shortcut and its art survive.
- **Update check:** "no release yet" (`ReleaseNotFound`: no `latest.json`, or a 404) counts as up to date. Only real request failures say to check the internet, and they're logged.
- **Controller in the desktop window** uses the same code as Couch mode (`ui/shared.js`: pad polling, D-pad focus movement, art with title-card fallback). B closes a dialog or goes back to Games, LB/RB switch tabs, Y scans, and View switches back to Couch mode, so opening the desktop view by accident is one button to undo.
- **Recent Games is not faked.** Steam's live "recent" order for shortcuts comes from its own in-memory app data (`rt_recent_activity_time`), seeded from the `LastPlayTime` SteamDrop already writes. Big Picture's Home can load before shortcut data is ready, which community plugins work around by patching Steam's UI. Per-app play data in `localconfig.vdf` is known to be overwritten by Steam Cloud sync. There's no documented, reliable file to write, so SteamDrop doesn't.

## Couch mode

- **One app, one extra tiny process.** Steam starts `SteamDrop.exe --couch`. That process starts `SteamDrop.exe --couch-open`, which either becomes SteamDrop or hands over to the one already in the tray (the single-instance plugin passes the argument along). Then it just waits until Couch mode closes, so Steam shows SteamDrop as running exactly while Couch mode is open. The app holds `%APPDATA%\SteamDrop\couch.lock` exclusively while the Couch window exists, and Windows releases it even if the app crashes. The waiting process checks that lock twice a second; it has no window and gives up after a minute if Couch mode never opens.
- **Which view opens from Steam:** Steam sets `SteamTenfoot=1` for anything started from Big Picture, and a Steam Deck sets `SteamDeck=1`. With "Auto", those open Couch mode and everything else opens the desktop window. The Steam shortcut now starts `--from-steam` (the older `--couch` still works). The process Steam started waits while **either** window exists (the lock is held by whichever is open), so switching views with F11 never makes Steam think SteamDrop stopped. A switch opens the new view before closing the old one.
- **Control bar:** "Hide" keeps the desktop window alive but hidden in the tray; Couch mode's "Back to Steam" closes Couch mode. Either way the Steam session ends, so Steam shows Play (see "No Resume" below). "Close" destroys the window and frees its memory (the original "destroy the window in the tray" rule), with no exit even if "Keep running in the tray" is off, because Close promises to keep watching. "Quit SteamDrop" asks "Stop adding new games?" first. On a controller: Y = Scan now, View = switch view, Menu = back to Steam. The desktop window reads only those two buttons, and only while a controller is connected.
- **Scan now** hands every new, non-empty folder in the watched folders to the same pipeline as the watcher. Folders still being copied are left to the watcher, which adds them once copying ends.
- **Couch mode is a second window in the same app**, so settings, the log and Steam changes all go through the same code and state. There are no two processes writing `data.json`.
- **Controller input** uses the Gamepad API's standard mapping (A, B, LB, RB, D-pad, left stick), so Xbox and PlayStation pads both work, read every frame only while the Couch window is open, since the API has no button events. Keyboard keys mirror every button, for testing and for remotes that send keys. Focus moves spatially to the nearest element in the pressed direction.
- **Couch mode never restarts Steam while it's open,** because it runs inside Steam. Changes are written right away. Steam may write its old list back (it does when it updates playtime as Couch mode exits), so every change made while Steam runs is remembered: `pending_removals` and `pending_adds`. These are written again whenever Steam is closed: at SteamDrop's start, before any Steam restart SteamDrop does, and after Couch mode. Leaving Couch mode with pending changes asks "Restart Steam to apply changes?". With "Restart now", the tray app waits until Couch mode (and the process Steam started) has exited, closes Steam, writes the changes while Steam is closed, and starts Steam again, in Big Picture if Steam was in Big Picture when it started SteamDrop. The same applies to "Add without restarting" on the desktop.
- **Delete game = Recycle Bin, never permanent.** SteamDrop only recycles on a plain drive letter whose drive type is "fixed" and where Windows reports a Recycle Bin. Network paths (UNC), USB sticks and memory cards are refused before anything touches them. It then deletes with "allow undo" plus Windows' own warning before any permanent delete. The folder is recycled first; only if that works are the shortcut and art removed. Hold A for 2 seconds to confirm.
- **SteamDrop's own artwork** (icon, Steam tile art, installer pictures) is drawn by `scripts/render-art.mjs` with the same code the app uses (`ui/grove.js`), then built into the app. The 16 px icon is a hand-placed pixel map; 24 and 32 px have their own grids; larger sizes enlarge those by whole numbers.
- **The installer checkbox** sits on the finish page under "Run" and "Create desktop shortcut". It runs `SteamDrop.exe --add-to-steam` before SteamDrop starts. It isn't shown for silent installs or updates, so a later "off" in Settings is respected. The uninstaller always removes SteamDrop's own shortcut, since it would point at a deleted program. If the setting is on and the shortcut is missing (Steam closed), SteamDrop puts it back at startup.

- **No "Resume", Play instead.** Steam's "Resume" focuses a window of the process it started, and that process (`--from-steam`) has none. A 1x1 window that started `SteamDrop.exe --resume` when activated was tried; it fired whenever it became the front window (Couch mode minimizing, SteamDrop quitting), and the processes it started could outlive SteamDrop and keep Steam showing it as running. So it's gone: the `--from-steam` process starts only the view, and exits as soon as no SteamDrop window is shown (hidden windows don't count), SteamDrop quits, or no SteamDrop process is left (checked twice a second). "Back to Steam" closes Couch mode instead of minimizing it, so Steam shows Play, and Play reopens it in about a second. If that process starts SteamDrop itself, it asks Windows to take it out of Steam's job (`CREATE_BREAKAWAY_FROM_JOB`, ignored when not allowed). The app still switches to Couch mode when a new Big Picture window opens during a Steam session (`SetWinEventHook`).
- **SteamDrop is never a game to Steam.** Before asking Steam to close (and when quitting), SteamDrop ends its own Steam-started processes (children of `steam.exe` named SteamDrop.exe, and what they started), because Steam waits for a running "game" before it closes. Steam's `RunningAppID` equal to SteamDrop's own shortcut doesn't count as a game. With a real game running, the restart waits for it.
- **One restart path:** `steam::restart_with` decides the mode, closes Steam (asking with `-shutdown`, checking every 250 ms with the Toolhelp process snapshot instead of starting `tasklist`), writes, and always starts Steam again, even if the write failed. It force-closes Steam only after 60 seconds. Adding and removing with Steam open write right away and keep the change pending; `library::request_restart` then runs one restart that applies all pending changes. Requests while one is waiting share it; changes during a restart get one follow-up restart.
- **Batches:** the watcher holds folders that finished copying, and game folders that disappeared, until 4 seconds after the last one and until no other folder is still on its way (at most 90 seconds). A deleted folder whose name reappears in the same batch is a move, handled as before. Deleted folders are never removed from Steam unasked.

- **Keep Big Picture in front** uses the same foreground hook. Two seconds after another window takes the focus (and still has it), Big Picture is brought back by briefly joining the front app's input (`AttachThreadInput`) and calling `SetForegroundWindow`, which Windows can still refuse. It leaves alone SteamDrop, Windows' sign-in, lock, permission and shell windows, Steam's own windows, the user's exceptions, anything whose parent chain leads to `steam.exe` (games and their launchers), and everything while a game runs.

- **Windows on top of Big Picture.** A second hook (`EVENT_OBJECT_SHOW`, top-level windows only) and Big Picture getting the focus both schedule one check two seconds later. If Big Picture has the focus and no game runs, every visible window above it in the stacking order that overlaps it, isn't click-through, isn't one of Windows' own shell windows and isn't excepted is placed right behind Big Picture with `SetWindowPos` (which also ends its always-on-top state). Nothing is closed, hidden or minimized.
- **Focus back after a game.** When a window of a process started from Steam (its parent chain leads to `steam.exe`) comes to the front while Big Picture exists, SteamDrop waits on that process handle (no polling). When it exits and, a moment later, the front window isn't Big Picture or something that may keep the focus, Big Picture is brought to the front. This doesn't depend on the "Keep Big Picture in front" setting.
- **Bringing a window to the front** tries three times: joining the front app's input; then with a press of a key that has no meaning (0xE8) so SteamDrop counts as the last app to get input; then with Alt, the usual way. Each refusal is logged as a problem.
- **Couch setup** is only a settings change made by the windows; the old values of the settings it touches are saved in `couch_setup_undo` so Undo puts them back, even after a restart.

- **Re-adding a shortcut edits it in place:** only AppName, Exe, StartDir and icon (and SteamDrop's own launch option) are set; every other field of an existing entry stays as Steam or the user left it.
- **Deleting is guarded twice:** the Recycle Bin rules, and a refusal for any "game folder" that is a drive root or contains a watched folder, Steam, SteamDrop's data or program, or the user's profile.
- **Quiet updates** leave a marker file (`updating-quietly`) so the restarted SteamDrop stays in the tray whatever arguments the old one had.

## Night Grove

- **One drawing module** (`ui/grove.js`): small canvases, whole pixels, enlarged without smoothing. Colors are CSS variables (`--sky-0`, `--leaf`, `--fruit`...) defined for every theme in `themes.css` (derived from the theme's base colors, hand-picked for Night Grove), so themes and their live preview recolor the forest.
- **The tree** has its own canvas over a cached drawing of trunk and leaves. Only a new game (blossom to fruit in 1.7 s, six fireflies) or a nudge (0.4 s) starts a timer at about 12 frames a second; when nothing moves there is no timer at all. Hidden windows and "reduce motion" jump straight to the end state. At most 60 fruits are drawn.
- **Sizes:** in Couch mode one forest pixel is a whole number of screen pixels (window height / 270, rounded), recomputed on resize, so the art stays crisp with any interface size. The desktop tree lives in the sidebar and hides in small windows, where the sidebar becomes a top bar again.
- **No thin outlines:** cards, panels, buttons and inputs are filled shapes with a hard shadow; selection uses a thick ring.
- **Pixelify Sans** (OFL 1.1) is for headings, names and tabs only; all body text stays Atkinson Hyperlegible.

## Left out on purpose

- Removing a shortcut automatically when its game folder is deleted. SteamDrop asks instead ("Remove selected" / "Keep in Steam"), because deleting things from Steam unasked felt wrong.
- Launch options, Steam collections/tags, and per-game controller settings. Steam already handles these for non-Steam games.
- Translations. Can be added later; the text lives in `ui/app.js` and the installer template.
